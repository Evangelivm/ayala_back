2.2 Editar el bloque "generator" en CADA schema
-------------------------------------------------
Archivos: prisma/schema.prisma, prisma_second/schema.prisma,
          prisma_third/schema.prisma

Antes:
  generator client {
    provider      = "prisma-client-js"
    output        = "../generated/prisma"
    binaryTargets = ["native", "debian-openssl-3.0.x"]
  }

Despues:
  generator client {
    provider     = "prisma-client"
    output       = "../generated/prisma"
    moduleFormat = "cjs"
  }

Notas:
  - moduleFormat = "cjs" es CLAVE: mantiene compatibilidad con NestJS/
    CommonJS. Sin esto, Prisma 7 emite ESM y rompe el build de Nest.
  - Se quita binaryTargets: ya no aplica (no hay motor Rust nativo que
    distribuir en v7, el cliente es TypeScript puro).
  - Ajustar el "output" segun cada carpeta (../generated/prisma,
    ../generated/prisma-second, ../generated/prisma-third).


2.3 Crear un prisma.config.ts por cada schema
-------------------------------------------------
Como son 3 proyectos independientes (3 datasources distintos), hacen
falta 3 archivos de config.

ayala_back/prisma.config.ts (para el principal):

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma/schema.prisma',
  });

ayala_back/prisma.config.second.ts:

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma_second/schema.prisma',
  });

ayala_back/prisma.config.third.ts:

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma_third/schema.prisma',
  });

Uso desde CLI (reemplaza al viejo --schema=...):

  npx prisma generate --config prisma.config.ts
  npx prisma generate --config prisma.config.second.ts
  npx prisma generate --config prisma.config.third.ts

OJO: en Prisma 7 el comando "prisma db execute" YA NO acepta --schema ni
--url. El flujo que se uso para verificar columnas nuevas (por ejemplo
la de centro_costos en partida) debe rehacerse con --config o con un
script node suelto que use el PrismaClient generado.


2.4 Actualizar PrismaService y PrismaThirdService
-------------------------------------------------
Archivo: src/prisma/prisma.service.ts

Antes:
  import { Injectable, OnModuleInit } from '@nestjs/common';
  import { PrismaClient } from '@generated/prisma';

  @Injectable()
  export class PrismaService extends PrismaClient implements OnModuleInit {
    async onModuleInit() {
      await this.$connect();
    }
  }

Despues:
  import { Injectable, OnModuleInit } from '@nestjs/common';
  import { PrismaMariaDb } from '@prisma/adapter-mariadb';
  import { PrismaClient } from '@generated/prisma';

  @Injectable()
  export class PrismaService extends PrismaClient implements OnModuleInit {
    constructor() {
      super({
        adapter: new PrismaMariaDb({
          host: process.env.DB_HOST,
          port: Number(process.env.DB_PORT) || 3306,
          user: process.env.DB_USER,
          password: process.env.DB_PASSWORD,
          database: process.env.DB_NAME,
        }),
      });
    }

    async onModuleInit() {
      await this.$connect();
    }
  }

Analogo en src/prisma/prisma-third.service.ts, usando las variables
correspondientes a DATABASE_URL_THIRD.

OJO CON EL FORMATO DE CONEXION:
  Hoy el .env tiene una URL unica por schema:
    DATABASE_URL=mysql://usuario:pass@host:puerto/basededatos
    DATABASE_URL_SECOND=mysql://...
    DATABASE_URL_THIRD=mysql://...
  El adapter @prisma/adapter-mariadb documenta mejor el esquema
  "mariadb://" que "mysql://". Para no arriesgar el parseo:
    a) Probar primero si funciona pasarle la URL cruda tal cual:
         new PrismaMariaDb(process.env.DATABASE_URL)
    b) Si falla o da error de parseo, parsear la URL manualmente con el
       modulo "url" de Node y pasar host/port/user/password/database
       como campos sueltos (mas seguro, evita el tema del esquema).

CORRECCIONES DESCUBIERTAS AL EJECUTAR (2026-08-22)
===================================================
La investigacion previa a correr esto no detecto estos puntos. Quedan
documentados aqui para la proxima vez (otro schema, otro proyecto, o si
hay que rehacer esto desde cero).

1. El campo "url" del bloque datasource NO se soporta en absoluto en v7,
   ni siquiera para que el CLI lo use. Hay que borrarlo del schema.prisma
   por completo:
     datasource db {
       provider = "mysql"
     }
   La URL real se pasa en dos lugares distintos y separados:
     a) prisma.config.ts (para el CLI / prisma generate):
          datasource: { url: process.env.DATABASE_URL }
     b) el adapter en el constructor de PrismaClient (para runtime):
          new PrismaMariaDb(process.env.DATABASE_URL!)
   IMPORTANTE: "prisma generate" funciona incluso si datasource.url es
   undefined (probado explicitamente). Esto es clave para el build de
   Docker, donde el .env todavia no esta disponible en la etapa donde
   se corre "prisma generate".

2. El cliente generado en v7 (provider = "prisma-client") YA NO tiene un
   archivo indice en la raiz (nada de "@generated/prisma" a secas). Hay
   que importar siempre desde el subpath /client:
     import { PrismaClient, Prisma } from '@generated/prisma/client';
   (antes era "from '@generated/prisma'"). Esto afecta a CUALQUIER
   archivo que importe PrismaClient o el namespace Prisma, no solo a
   los PrismaService. En este repo se tuvo que corregir en:
     src/prisma/prisma.service.ts
     src/prisma/prisma-third.service.ts
     src/acarreo/acarreo.service.ts
     src/programacion/programacion.service.ts
     src/gre/gre-extendido-crud.controller.ts
     src/search/search.service.ts
     src/contabilidad/contabilidad.service.ts
     src/contabilidad/seed-catalogos.ts

3. El cliente generado en v7 es codigo TypeScript fuente (client.ts,
   models.ts, enums.ts, etc.), NO viene precompilado a .js ni trae su
   propio package.json (a diferencia de v6). Lo compila el propio
   "nest build" (tsc) igual que el resto de src/, porque este proyecto
   no tiene "include"/"exclude" en tsconfig.json que excluya la carpeta
   generated/. No hace falta ningun paso extra para compilarlo, pero:

   OJO: si no se borra la carpeta generated/<schema>/ ANTES de correr
   "prisma generate" por primera vez en v7, quedan mezclados los
   archivos viejos de v6 (index.js, los binarios query_engine-*.dll.node
   / .so.node, package.json con "version": "6.19.0") junto a los nuevos
   .ts de v7. Esto puede hacer que un import "resuelva" al archivo
   viejo sin dar error (falso positivo). Siempre correr:
     rm -rf generated/prisma generated/prisma-second generated/prisma-third
   antes de regenerar con los nuevos generator blocks.

4. "@prisma/client/runtime/library" (usado para importar el tipo
   Decimal) ya no existe en v7. El path nuevo es:
     import { Decimal } from '@prisma/client/runtime/client';
   Afectó a: src/factura/interfaces/factura-item.interface.ts,
   src/factura/interfaces/factura.interface.ts,
   src/factura/services/factura-detector.service.ts

5. TypeScript es estricto con "process.env.X" (tipo string | undefined)
   pasado al constructor de PrismaMariaDb (que pide string | PoolConfig).
   Se resolvio con non-null assertion (!), asumiendo que la env var
   siempre esta seteada en runtime (igual que asumia el codigo viejo):
     new PrismaMariaDb(process.env.DATABASE_URL!)

6. El adapter @prisma/adapter-mariadb SI acepta la URL cruda tal cual
   viene en .env (formato "mysql://user:pass@host:puerto/db"), no hizo
   falta parsearla a campos sueltos (host/port/user/password/database).
   Probado y confirmado contra los 3 schemas, incluido el servidor
   remoto de prisma_third.

7. dotenv (usado dentro de los prisma.config*.ts) imprime un mensaje
   tipo publicidad en consola al llamar a config() (algo como
   "tip: auth for agents [www.vestauth.com]" o "secrets for agents
   [www.dotenvx.com]"). Es un comportamiento conocido de versiones
   recientes de dotenv, no es un error ni algo que haya que arreglar,
   pero puede sorprender si no se esperaba verlo en los logs.

8. El Dockerfile original solo copiaba y generaba el schema principal
   (prisma/) antes de "npm run build". Con 3 schemas/configs
   independientes hay que copiar tambien prisma.config.ts,
   prisma.config.second.ts, prisma.config.third.ts, prisma_second/ y
   prisma_third/, y correr "prisma generate --config <archivo>" para
   cada uno por separado (ya no basta un solo "npx prisma generate" a
   secas). Se corrigio en el Dockerfile, PERO OJO: este fix del
   Dockerfile no se probo con un "docker build" real (no se corrio en
   esta sesion) - conviene validarlo antes de desplegar.

9. Se agrego "dotenv" como devDependency explicita (antes solo estaba
   como dependencia transitiva via @nestjs/config), porque los
   prisma.config*.ts la importan directamente con "import 'dotenv/config'".

10. Efecto colateral no relacionado con Prisma: al reinstalar paquetes,
    "typescript" (rango ^5.7.3 en package.json, sin tocar) subio de

    aparecio como parte del mismo "npm install" y hubo que arreglarlo
    para que el build siguiera pasando.
