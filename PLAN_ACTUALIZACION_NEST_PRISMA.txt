2.2 Editar el bloque "generator" en CADA schema
-------------------------------------------------
Archivos: prisma/schema.prisma, prisma_second/schema.prisma,
          prisma_third/schema.prisma

Antes:
  generator client {
    provider      = "prisma-client-js"
    output        = "../generated/prisma"
    binaryTargets = ["native", "debian-openssl-3.0.x"]
  }

Despues:
  generator client {
    provider     = "prisma-client"
    output       = "../generated/prisma"
    moduleFormat = "cjs"
  }

Notas:
  - moduleFormat = "cjs" es CLAVE: mantiene compatibilidad con NestJS/
    CommonJS. Sin esto, Prisma 7 emite ESM y rompe el build de Nest.
  - Se quita binaryTargets: ya no aplica (no hay motor Rust nativo que
    distribuir en v7, el cliente es TypeScript puro).
  - Ajustar el "output" segun cada carpeta (../generated/prisma,
    ../generated/prisma-second, ../generated/prisma-third).


2.3 Crear un prisma.config.ts por cada schema
-------------------------------------------------
Como son 3 proyectos independientes (3 datasources distintos), hacen
falta 3 archivos de config.

ayala_back/prisma.config.ts (para el principal):

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma/schema.prisma',
  });

ayala_back/prisma.config.second.ts:

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma_second/schema.prisma',
  });

ayala_back/prisma.config.third.ts:

  import 'dotenv/config';
  import { defineConfig } from 'prisma/config';

  export default defineConfig({
    schema: 'prisma_third/schema.prisma',
  });

Uso desde CLI (reemplaza al viejo --schema=...):

  npx prisma generate --config prisma.config.ts
  npx prisma generate --config prisma.config.second.ts
  npx prisma generate --config prisma.config.third.ts

OJO: en Prisma 7 el comando "prisma db execute" YA NO acepta --schema ni
--url. El flujo que se uso para verificar columnas nuevas (por ejemplo
la de centro_costos en partida) debe rehacerse con --config o con un
script node suelto que use el PrismaClient generado.


2.4 Actualizar PrismaService y PrismaThirdService
-------------------------------------------------
Archivo: src/prisma/prisma.service.ts

Antes:
  import { Injectable, OnModuleInit } from '@nestjs/common';
  import { PrismaClient } from '@generated/prisma';

  @Injectable()
  export class PrismaService extends PrismaClient implements OnModuleInit {
    async onModuleInit() {
      await this.$connect();
    }
  }

Despues:
  import { Injectable, OnModuleInit } from '@nestjs/common';
  import { PrismaMariaDb } from '@prisma/adapter-mariadb';
  import { PrismaClient } from '@generated/prisma';

  @Injectable()
  export class PrismaService extends PrismaClient implements OnModuleInit {
    constructor() {
      super({
        adapter: new PrismaMariaDb({
          host: process.env.DB_HOST,
          port: Number(process.env.DB_PORT) || 3306,
          user: process.env.DB_USER,
          password: process.env.DB_PASSWORD,
          database: process.env.DB_NAME,
        }),
      });
    }

    async onModuleInit() {
      await this.$connect();
    }
  }

Analogo en src/prisma/prisma-third.service.ts, usando las variables
correspondientes a DATABASE_URL_THIRD.

OJO CON EL FORMATO DE CONEXION:
  Hoy el .env tiene una URL unica por schema:
    DATABASE_URL=mysql://usuario:pass@host:puerto/basededatos
    DATABASE_URL_SECOND=mysql://...
    DATABASE_URL_THIRD=mysql://...
  El adapter @prisma/adapter-mariadb documenta mejor el esquema
  "mariadb://" que "mysql://". Para no arriesgar el parseo:
    a) Probar primero si funciona pasarle la URL cruda tal cual:
         new PrismaMariaDb(process.env.DATABASE_URL)
    b) Si falla o da error de parseo, parsear la URL manualmente con el
       modulo "url" de Node y pasar host/port/user/password/database
       como campos sueltos (mas seguro, evita el tema del esquema).
